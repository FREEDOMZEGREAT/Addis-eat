# Data Fetching

The app uses server-rendered reads by default and uses SWR only for the client-side live-data views: menu search (`src/app/menu/SearchBox.jsx`), the orders-page status badge (`src/app/orders/OrderStatus.jsx`), and the delivery tracker (`src/app/track/[id]/OrderTracker.jsx`). They share an in-memory cache configured in `src/app/swr-provider.jsx`, so repeated keys are deduped and cached for the session. TanStack Query is not used. The cart context in `src/app/providers.jsx` is unrelated to server data.

## Storage notes

The dish catalog in `src/lib/dishes.js` is seeded from static module data into an in-memory store (hung off `globalThis`) with an `available` flag; the staff admin workspace adds, edits, and removes items and toggles availability, and those edits reset when the server restarts. Registered accounts are handled by `src/lib/users.js` in an in-memory store mirrored to the ignored `data/users.json` file when the filesystem is writable; on read-only or ephemeral hosts (e.g. Vercel) they fall back to memory only, so accounts do not survive restarts there. When `DATABASE_URL` is set, both accounts and orders use Neon Postgres instead (tables are initialized automatically, and the `dispatched_at` and `tracking` columns are added with idempotent migrations). Without it, orders use an in-memory store shared across the process. Delivery routes are fetched from an external OSRM server (`OSRM_BASE_URL`, default `https://router.project-osrm.org`) when staff dispatch an order, and the resulting geometry is stored with the order. The cart lives in `src/app/providers.jsx` and is persisted to `localStorage` (key `addis-eats-cart`), so it survives client navigation and full page reloads.
